# Voice mode — back to basics (2026-07-25)

Status: **active**. Supersedes the delivery plan in `redesign-2026-07-13.md`; the
conceptual model in `00-overview.md` (turn machine, heard-vs-generated, background
threads) still stands and is NOT being rewritten. This document is about the layer
that was skipped: **the conversation loop the user can actually see and trust.**

## 0. The report

> "There's a minor bug where if you turn off the mic, it immediately registers it
> as a microphone-not-allowed error. But primarily it just does not work — there's
> no way for it to read the voice, whatever you're saying doesn't show up, and
> there's no handling of this."

Both are real. Neither is an engine problem.

## 1. What is actually broken

Verified this session, not inferred:

- **The engine is healthy.** `/voice/health` reports `stt.available: true`
  (`base.en`), `tts.available: true` (Kokoro `af_heart`), device `cpu`. A real
  HTTP round-trip with a device token returns an exact transcript in 0.8 s; TTS
  renders 2.85 s of audio in 1.3 s. The models, the routes, the auth, and the
  public-edge proxy all work.

- **B1 — The server STT path has no feedback channel at all.** `partial` is
  written in exactly one place, `voiceSession.ts:444`, inside `armBrowserListen`.
  On the server path (the default, because server STT *is* available, so
  `detectCaps` picks it) nothing you say is ever surfaced. The eager-endpoint
  path *does* transcribe mid-utterance, but it pushes into `this.segs`, which is
  never rendered. The user's screen is identical whether the system is listening
  perfectly or completely deaf.

- **B2 — The VAD threshold is a blind constant.** `startThreshold = 0.06` RMS,
  against a capture chain running `echoCancellation + noiseSuppression +
  autoGainControl`. If a given mic never clears it, `onSpeechStart` never fires,
  so `onSpeechEnd` never fires, so no segment is ever cut, transcribed, or sent —
  forever, with no error, no timeout, and no diagnostic. This is the "just does
  not work" failure, and it is unfalsifiable from the UI.

- **B3 — Short utterances are dropped silently.** `onSpeechEnd` gates on
  `blob.size >= 1200`; below that, `spoke` is false, so not even the "Didn't catch
  that" message fires. It re-arms as if nothing happened.

- **B4 — Muting the mic is routed through the permission-denied path.**
  `setMicEnabled(false)` calls `mic.stop()` but never touches `browserAbort`, so
  an in-flight recognizer keeps running and errors. The handler at
  `voiceSession.ts:452` tests `/not-allowed|denied|service-not-allowed/i`, sets
  `fatal = true`, and `Chat.tsx:660` drops `voiceOn` on any fatal. Deliberately
  muting therefore reads as "Microphone permission denied" and kills the session.

- **B5 — There is no modality model, only four booleans.** The wanted behaviour
  (talk-in/read-out, type-in/listen-out, both, either) is spread across
  `mic_enabled`, `speak_replies`, `tts_provider: "off"`, and `typing_hold`,
  resolved in three different places (`resolveProviders`, `setPrefs`,
  `beginReply`). No single value says what mode the conversation is in, so the UI
  cannot show it and the surfaces cannot vary it.

- **B6 — Nothing distinguishes "no permission" from "no secure context".**
  `mic.start()` calls `navigator.mediaDevices.getUserMedia` unguarded. Off HTTPS
  and off localhost, `navigator.mediaDevices` is `undefined` and this throws a
  TypeError that surfaces as `mic: TypeError…`. This is the single most likely
  thing to bite the Expo WebView and any plain-http tailnet origin, and it is
  reported as a generic mic failure.

The through-line: **every failure mode in this system is silent.** The concept
work (`00-overview.md`) was about a conversation that knows what you heard. The
implementation shipped a conversation that cannot tell you what *it* heard.

## 2. What good looks like (research grounding)

The current production consensus on turn-based voice agents, which the existing
design predates:

- **Stream partial transcripts.** Do not wait for the full utterance. Partials are
  both a latency win and, more importantly here, the user's proof that the system
  is alive. Sub-500 ms STT response is the bar for feeling conversational.
- **Endpointing is a decision, not a timer.** Silence-only endpointing is the weak
  baseline; the current stack layers a semantic completeness check on the partial
  text. Workshop already has the text-only version of this (`incomplete()`), and
  it is on the right side of this line.
- **Barge-in requires full duplex.** STT and TTS on independent simultaneous
  streams, never alternating. Workshop does this correctly (continuous recorder +
  echo-subtracted VAD + pre-roll).
- **Latency budget** accumulates per stage: endpointing 50-200 ms, STT finalize
  50-150 ms, LLM TTFT 150-500 ms, TTS first byte 75-200 ms.
- **Local Whisper streams via a sliding/growing window**, not by chopping audio
  into independent chunks — chopping destroys accuracy at the seams. Measured
  partial latency of 200-400 ms is achievable on CPU with a small model.
- **WebView is its own platform.** `getUserMedia` in iOS WKWebView needs
  `NSMicrophoneUsageDescription` (present in `mobile/app.json`) *and* the host to
  answer `decideMediaCapturePermissionFor`, or the prompt never appears and the
  call hangs. It is a distinct capability tier, not "mobile web".

Workshop's turn machine is, structurally, ahead of most of this. What it lacks is
the incremental feedback loop and the honesty layer.

## 3. The model

### 3.1 The modality matrix is first-class

One concept replaces five booleans:

```
input_mode  : "voice" | "text" | "both"     (default: both)
output_mode : "voice" | "text" | "both"     (default: both)
```

Any of the nine combinations is legal and is what the operator asked for:

| | output voice | output text | output both |
|---|---|---|---|
| **input voice** | hands-free call | dictate, read the reply | dictate, hear + read |
| **input text** | type, listen | plain chat | type, hear + read |
| **input both** | talk or type, listen | talk or type, read | the default |

- `input_mode` decides whether the mic lane runs. `text` means the mic is off *by
  intent* — a mic error in that state is not an error, it's the configuration.
- `output_mode` decides whether TTS runs. `text` means captions only; the
  heard-vs-generated bookkeeping still runs (text you have read is "heard"), so
  interrupt/resume semantics are identical in every mode.
- `mic_enabled` / `speak_replies` remain in the stored prefs and are derived both
  ways, so existing `voice-prefs.json` files keep working.

### 3.2 The input lane always reports

Three-stage, on every path:

1. **Signal** — a live raw mic level (pre-echo-subtraction), always visible while
   the input lane is on. Answers "is the mic even connected".
2. **Partial** — incrementally growing transcript text while you speak, on the
   server path as well as the browser path. Answers "is it hearing words".
3. **Committed** — the finalized utterance that became a turn.

Server-path partials use a **growing-window preview**: `MediaRecorder.requestData()`
flushes the current segment's buffer, and the accumulated chunks from the segment
start form a valid, decodable container. That blob is transcribed by a small
preview model (`tiny.en`) purely for display; it never enters `segs` and never
becomes the committed text. The authoritative transcript is still one clean
`base.en` pass over the whole segment at the endpoint. Full accuracy, live
feedback, no seam artifacts.

Only one preview may be in flight at a time; if the previous one has not returned,
the tick is skipped. Preview is skipped entirely once a segment passes a duration
ceiling (the pass would land later than the endpoint anyway).

### 3.3 Nothing fails silently

- **Noise-floor calibration.** On listen start, sample the ambient level for
  ~1.2 s and set the onset threshold to `max(floor * 2.5, sensitivity_floor)`.
  The blind constant becomes a measurement. Recalibrates whenever the input lane
  restarts.
- **No-signal watchdog.** Input lane on, state `listening`, and the peak raw level
  over a rolling window is effectively zero → surface "No signal from the
  microphone" with the resolved device tier. Distinct from "signal present but
  under threshold", which surfaces "Mic level is low" and auto-drops the
  threshold once.
- **Deaf watchdog.** Input lane on, level *is* crossing the floor, but no
  `onSpeechStart` in N seconds → the same low-level path.
- **Delete the `blob.size < 1200` drop.** If the VAD said speech happened, always
  attempt transcription and always report the outcome.
- **Preflight, with the real reason.** Before `getUserMedia`: check
  `window.isSecureContext` and `navigator.mediaDevices`. Missing → "Voice needs a
  secure origin (https or localhost); this page is http://…". `NotAllowedError` →
  a genuine permission message with the recovery step. `NotFoundError` → "No
  microphone found". No more `mic: TypeError…`.

### 3.4 Intentional-off is never an error

A `micSuspended` flag is set for the whole time the input lane is off by
configuration. While set: `browserAbort()` is called, the recognizer is torn down,
and any error arriving from the capture layer is swallowed rather than surfaced or
escalated to `fatal`. Recognizer `aborted` and `no-speech` are classified as
benign everywhere, separately from real permission denial.

### 3.5 Diagnostics are a surface, not a console

A **Diagnostics** section in Voice settings showing: resolved STT/TTS tier and
model, device, secure-context status, live raw level meter, measured noise floor,
active threshold, last endpoint→first-audio latency, and a **Test microphone**
button that records 3 s and prints the transcript it got back. One look answers
"is it me, the mic, the model, or the network".

### 3.6 Surface tiers

The same session engine, three capability tiers, chosen by probe not by guess:

| tier | STT | TTS | notes |
|---|---|---|---|
| desktop/mobile web (https) | server `base.en` + `tiny.en` preview | server Kokoro | full duplex, barge-in, previews |
| Expo WebView (`speech` capability) | native `SFSpeechRecognizer` on-device | native `AVSpeechSynthesizer` | native gives its own partials; no server round-trip |
| degraded (no server, no native) | browser `SpeechRecognition` | browser `SpeechSynthesis` | partials come free from the recognizer |

Insecure origin is a **fourth outcome**, not a tier: voice input is unavailable and
says so, while `output_mode` text still works, so the chat is never bricked.

## 4. Change plan

Ordered; each step is independently shippable.

| # | Change | Files |
|---|---|---|
| 1 | Preview STT model (`tiny.en`) + `preview` flag on `/voice/stt`; report both models in health | `backend/services/voice_engine.py`, `backend/routes/voice.py` |
| 2 | `input_mode` / `output_mode` in prefs, derived both ways from `mic_enabled` / `speak_replies` | `backend/routes/voice.py`, `frontend/src/lib/voiceSession.ts` |
| 3 | Mic preflight + typed capture errors + raw level + noise-floor calibration + `snapshot()` growing-window blob | `frontend/src/lib/voice.ts` |
| 4 | Session: modality resolution, preview loop, `micSuspended`, watchdogs, remove the size gate, diagnostics in the snapshot | `frontend/src/lib/voiceSession.ts` |
| 5 | Live partial + signal in the composer strip; mic mute never exits voice | `frontend/src/components/Chat.tsx` |
| 6 | Modality matrix control + Diagnostics + Test microphone | `frontend/src/components/VoiceSettings.tsx`, `frontend/src/styles/components.css` |

Out of scope for this pass, deliberately: replacing silence endpointing with a
learned turn-detector model (the text heuristic stays), a WebRTC/full-duplex
transport (the recorder+VAD design is adequate at these latencies), and any change
to the background-thread queue or heard-vs-generated bookkeeping — those parts of
the original design are sound and untouched.

## 5. Acceptance

Voice mode is fixed when, on a fresh session:

1. Speaking shows growing text within ~1 s, before the reply starts.
2. A mic that produces no signal says so within ~4 s, naming the reason.
3. Muting the mic mutes the mic: no error, session stays live, composer works.
4. Every one of the nine input/output mode combinations is reachable and behaves.
5. An insecure origin explains itself and leaves text chat working.
6. Test microphone returns a transcript, or the specific reason it could not.
