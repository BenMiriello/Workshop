# Deployments in Workshop — proposal (2026-07-18)

Status: **proposal**, not built. Sits above `docs/platform-redesign/entity-model-2026-07-18.md` and `docs/app-platform-runner.md`. No code changes yet; each phase below is a separately-approvable unit.

## 1. What we're solving

The operator can already **run** a project locally (`app_runner`, `workshop.app.json`) and **share it on the local marketplace** (Share section). What he can't do from Workshop today:

- Point a project at a hosted target (Cloudflare Pages first) and press "Deploy".
- See which version/branch is live, what changed since, and roll back.
- Manage deploy credentials the same way he manages other secrets.
- Trigger a deploy from a chat/ticket/agent, or schedule one.

There's **no Cloudflare API integration** in the tree today — only a manually-authorized cloudflared **tunnel** exposing local `:8001` / `:8002`. Adding "hit the Cloudflare API and publish a build" is greenfield.

Also: no `benmiriello` project in `.runtime/projects.json` yet. Whatever we build has to work for a project that's about to be registered, not one already carrying history.

## 2. Recommendation (short version)

Model deployment as a **first-class Project sub-entity** (`Deploy` = target binding, `DeployRun` = attempt). Reuse the existing **Run/Job** infrastructure for the deploy attempt itself, so a deploy shows up in the same Work → Runs surface as everything else. Ship a **Cloudflare Pages** provider first (the smallest, most useful cut — supports static SPAs and edge Workers with the same API surface), behind a `providers/` seam that can grow Fly.io, Vercel, and a self-hosted "own-VPS" target later without refactoring the entity model. UI = one **Deploys panel** on `ProjectDetail.tsx` plus a workspace-level **/deploys** index for cross-project view.

Main tradeoff: this adds a new entity kind — but the alternative (just tagging Runs with a "deployment" trigger) loses the target/history/rollback affordances that make deploy management worth building.

## 3. Entity model

Two new nouns. Sit inside the existing model, don't replace anything.

### 3.1 `Deploy` (target binding, config)

Per-project record of "this project deploys **here**". A project can have 0..N.

```jsonc
{
  "id": "dep_a1b2",
  "project_slug": "benmiriello",
  "name": "prod",                       // "prod" | "preview" | free-form
  "target": {
    "kind": "cloudflare-pages",         // provider seam
    "project_name": "benmiriello",      // CF Pages project
    "account_id": "…"                   // resolved from creds
  },
  "source": {
    "kind": "git-branch",
    "branch": "main",                   // ref that "prod" tracks by default
    "build": {                          // borrows workshop.app.json shape
      "cmd": "npm run build",
      "output_dir": "dist",
      "node_version": "20"
    }
  },
  "domain": "benmiriello.com",          // display; provider owns DNS
  "autonomy": "reactive",               // reactive|supervised|autonomous
  "created_at": "…",
  "last_run_id": "run_…",               // pointer, denormalized
  "current": {                          // populated after successful run
    "run_id": "run_…",
    "commit_sha": "…",
    "deployed_at": "…",
    "url": "https://benmiriello.com"
  }
}
```

Persisted at `.runtime/deploys.json` alongside `apps.json`/`projects.json`. One-writer via existing `_write_json_atomic` pattern.

### 3.2 `DeployRun` (attempt) — **is a Run/Job, not a new table**

Every deploy attempt is a `Job` in `.runtime/jobs.jsonl` with:

- `trigger`: `manual` | `event` (git push webhook) | `cron` | `loop`
- `project_slug`: bound
- `kind`: `"deploy"` (new value; existing values keep working)
- `binding`: `{deploy_id, commit_sha, ref}`
- Standard `queued → running → done|failed|cancelled`
- `output_summary`: last N lines of the build/upload log, plus the resulting URL

This is the *only* thing that appears in Work → Runs. Deploy attempts don't create a Ticket — they run direct against the Deploy binding. (Rationale: a Ticket implies "work to plan and negotiate"; a deploy is an operation, not a change to plan.)

### 3.3 Where credentials live

Reuse `secrets_store` (per-project, 0600, presence-only status API). Provider drivers declare `env_requirements` the same way `app_runner` does:

```jsonc
// providers/cloudflare_pages.py declares:
{
  "env_requirements": [
    { "key": "CF_API_TOKEN",  "required": true,  "description": "Pages:Edit + Account:Read" },
    { "key": "CF_ACCOUNT_ID", "required": true,  "description": "Cloudflare account ID" }
  ]
}
```

Values are stored either:

- **Per-project** (`.runtime/secrets/<project>.json`) — the default, matches today's pattern.
- **Workspace** (`.runtime/secrets/_workspace.json`) — new, for creds shared across projects. Reads fall through from project → workspace.

*Stores* remain the wrong place for these (Stores are typed app data with adapters). *Grants* remain irrelevant (Grants mediate app→data access, not deploy-time provider auth).

## 4. Provider: Cloudflare Pages (first)

Direct Cloudflare API, not Wrangler CLI (fewer moving pieces, no Node runtime in the deploy path, easier logging).

### 4.1 The deploy flow

```
1. Resolve source          git checkout <ref> into .runtime/build/<deploy_id>/src
2. Build                    run source.build.cmd; wait; capture log; verify output_dir
3. Package                  tar.gz the output_dir
4. Upload                   POST /accounts/{acc}/pages/projects/{proj}/deployments
                             (direct-upload form, ~50MB limit — chunked if larger)
5. Poll                     GET /accounts/{acc}/pages/projects/{proj}/deployments/{id}
                             until status ∈ {success, failure}
6. Land                     write current.{url, commit_sha, deployed_at} on the Deploy
                             update last_run_id
```

Each step emits a `Job` progress line (existing pattern). Failed step → Job `failed` with the failing step named in `output_summary`. Rollback = a `POST` on an older deployment's `id` with `"aliases": ["production"]`, wrapped as its own Job kind `"deploy-rollback"`.

### 4.2 The provider seam

```python
# backend/services/deploy_providers/base.py
class DeployProvider(Protocol):
    kind: str                                   # "cloudflare-pages"
    def env_requirements(self) -> list[dict]: ...
    def preflight(self, deploy: Deploy, env: dict) -> Preflight: ...  # cred check + project exists
    def build(self, deploy, workdir, log) -> BuildResult: ...          # local; produces output_dir
    def upload(self, deploy, build, env, log) -> UploadResult: ...     # provider-specific
    def status(self, deploy, upload_ref, env) -> Status: ...           # poll
    def rollback(self, deploy, to_run_id, env, log) -> RollbackResult: ...
    def list_history(self, deploy, env) -> list[HistoryEntry]: ...     # optional
```

Adding Fly.io, Vercel, or "own-VPS" (rsync over SSH) later is one file each. The Deploy record's `target.kind` picks the provider.

### 4.3 Egress guard

Egress guard blocks `api.cloudflare.com` from arbitrary tools. Add a narrow exemption keyed on the deploy runner process (same shape as the existing tunnel exemption) — not a blanket "workshop can hit CF". Guard shape: allow when caller is `deploy_runner` AND target is `api.cloudflare.com` AND method is one of the deploy endpoints. Deny-by-default everywhere else.

## 5. UI

Two surfaces.

### 5.1 Per-project: `<DeploysPanel slug={slug} />`

Slots into `ProjectDetail.tsx` between **Run & Deploy** (which is really "Run") and **Environment**. Naming: rename `AppServicesPanel` header from "Run & Deploy" to just **"Run"** so the two aren't confused.

```
Deploys
────────────────────────────────────
[+ Add target]

prod · cloudflare-pages · main            [ Deploy ] [ ⋯ ]
    live: benmiriello.com
    v: c8a91f (2 hours ago)  ← last successful run
    3 commits ahead on main             ← from repo.branches
    Autonomy: reactive
    History › (opens run list scoped to this deploy)

preview · cloudflare-pages · any-branch    [ Deploy from ▾ ]
    last: c3f2e1 (feature/hero — 12m ago) · failed at Build step
    …
```

Row surfaces (using existing primitives):

- **StatusPill** — from the last Run for this Deploy (ok/running/warn/danger).
- **Deploy button** — Edit-mode-gated (`ConfirmDialog` when prod). Opens a compact modal: ref picker (branch/tag/commit, defaults to `source.branch`), optional deploy-message, "Start deploy" → posts a Job → panel updates in place.
- **History** — inline expandable list of last N runs (linked to `/work/runs/<id>` for the full log).
- **Rollback** — right-click / `⋯` menu on any historical successful run → confirms → posts a `deploy-rollback` Job.
- **Autonomy control** — reuses `AutonomyPanel` shape (reactive/supervised/autonomous). `autonomous` = auto-deploy on push to `source.branch`.

Cred prompt: if `preflight` fails (missing CF_API_TOKEN), the row shows a **StateBlock** with kind=warn linking to Environment panel with the specific missing keys pre-highlighted. Same pattern the Run panel already uses.

### 5.2 Workspace: `/deploys`

Top-level page. Table across all projects, one row per **Deploy** (target), most-recently-active first. Columns: Project · Target · Domain · Version · Status · Autonomy · Last run · Actions.

Filter chips (mirroring Chats.tsx pattern): `All / Prod / Preview / Failed / Autonomous`.

Purpose: single "what's live where" view without opening each project. Also the surface where the operator flips the workspace-level Deploys autonomy override (independent of the workshop autonomy override — different kill switch, different failure mode).

### 5.3 In chat / tickets

Once Runs handle deploys, a triager can already invoke them. Add one thin affordance later: chat command `/deploy <project> [<target>]` posts a Ticket + Job. Not in Phase 1.

## 6. Ralph / autonomy interaction

Deploys respect the same effective-autonomy overlay as agents (`autonomy_override.json`). When the workshop override is engaged, `autonomous` deploys become `supervised` (queue + await manual release), not `off` — because the operator often wants "still show me the diff, just don't ship it" during a freeze.

Per-Deploy autonomy override at `.runtime/deploys/<deploy_id>/autonomy-override.json` — mirrors the pattern from agent-autonomy so the two systems can share the same helper (`autonomy_override.read()`).

## 7. Backend surface (routes)

New router `backend/routes/deploys.py`:

- `GET  /api/projects/{slug}/deploys` — list
- `POST /api/projects/{slug}/deploys` — create (name, target, source)
- `PATCH /api/projects/{slug}/deploys/{deploy_id}` — edit source/autonomy
- `DELETE /api/projects/{slug}/deploys/{deploy_id}` — remove (soft-delete, keep run history)
- `POST /api/projects/{slug}/deploys/{deploy_id}:deploy` — kick a run (body: `{ref, message}`)
- `POST /api/projects/{slug}/deploys/{deploy_id}:rollback` — kick a rollback (body: `{to_run_id}`)
- `GET  /api/deploys` — cross-project list for `/deploys`
- `GET  /api/deploys/providers` — list provider kinds + env_requirements (drives the "Add target" modal)

Runs surface unchanged. The Deploys panel just queries `/api/jobs?project_slug=…&kind=deploy&binding.deploy_id=…`.

## 8. Rollout order

Each phase self-contained and independently landable.

**Phase 1 — infra + provider skeleton (backend only).** Deploy record + `.runtime/deploys.json`; provider seam; Cloudflare Pages provider (preflight + build + upload + status); job kind `deploy`; new routes. No UI. Manually testable via curl. **Unblocks everything.**

**Phase 2 — DeploysPanel.** Read-only first (list + status + history), then Deploy button (Edit-mode-gated), then rollback. `benmiriello` project registered in this phase.

**Phase 3 — /deploys index page.** Route + table + filter chips. Workspace autonomy override for deploys.

**Phase 4 — autonomy: auto-deploy on push.** New event source that watches the project's git remote (webhook or poll — depends on where the repo actually lives). Only after Phase 3 lands so the safety valve exists first.

**Phase 5 — second provider.** Whichever the operator wants next — likely Fly.io or a plain "own-VPS via rsync+ssh" target. Validates the provider seam.

**Phase 6 — chat + ticket integration.** `/deploy` command; Deploy button inside a Ticket detail; agent-issued deploys go through the same autonomy overlay.

## 9. Explicit non-goals (Phase 1)

- **No DNS management.** CF DNS records stay hand-managed; Deploys only *point at* domains they don't provision. Adding DNS is a later opt-in.
- **No preview URLs in PRs.** CF Pages gives you a `pages.dev` URL per deployment for free; we surface it, we don't push it back to GitHub as a PR comment.
- **No multi-region / promote flow.** Prod is prod. Rollback is the safety net. Blue-green comes later if it matters.
- **No secrets rotation UI.** Env-panel already covers set/replace; that's enough.
- **No cost/usage surfacing.** Later.
- **No SSR framework detection.** Static output only. When the operator has an SSR project, we add framework-specific build presets — not before.

## 10. Open questions (small, blocking Phase 1 only where noted)

- **Where does `benmiriello` the site live in git?** If it's not yet a repo, it needs to be one before any deploy target can bind. This is a project-scaffolding question, not a deploy-system question — but it blocks the first live test.
- **CF Pages "project" naming.** Match the workshop project slug 1:1, or allow renames? Recommend 1:1 for Phase 1, add rename later.
- **Build in-process vs. subprocess vs. docker?** Recommend subprocess-with-timeout for Phase 1 (matches how `app_runner` starts services). Docker later if we hit sandbox needs.
- **Do we log build output to a file per run, or only into the Job's `output_summary`?** Recommend a per-run file at `.runtime/deploys/<deploy_id>/runs/<run_id>.log`, with `output_summary` being the last ~40 lines. Matches how `jobs.py` already handles evidence blobs. **Non-blocking** — can be added Phase 2.

## 11. Related design that doesn't need to move for this

- `workshop.app.json` — untouched. Its `build` describes "how to prep for a resident local process"; Deploy's `source.build` describes "how to produce a shippable artifact". Both formats look identical because the operations *are* similar, but the semantics differ and the code paths shouldn't share.
- Marketplace publish (Share section) — unchanged. Marketplace is the *social/discovery* surface; Deploys is the *ops* surface. A project can be marketplace-published and independently CF-Pages-deployed.
- Repository / Branches panels — unchanged. Deploy references a ref; it doesn't manage refs.
