Measured 2026-08-25 on `.runtime/usage.jsonl` (5,040 rows, 6,544,418,988 raw tokens, 2026-07-15 to 2026-08-25).

**The test suite writes into the real production ledger.** `usage_ledger.LEDGER_PATH` resolves at import from the real path and only 5 test files patch it. 4,208 of 5,040 rows (83.5%) are test writes: 1,724 rows of exactly 11 tokens carry `run: "run-ctx"` (from `test_context_measurement.py:93`, whose `_result()` yields cache_read 1 + output 10), 671 rows carry `run: "run-second-prompt"`, and 1,801 of 1,813 compaction rows name chat ids that never existed on disk (134 real thread dirs vs 1,695 distinct ids). They are only 0.32% of the tokens, so they wreck every COUNT and almost no TOTAL. Real chat: 716 rows, median 4,070,432, p80 15.0M, max 120M.

**Three metering defects, all in `build_streaming.py`.** (1) `spend_sum` (`:2583`) sums stream FRAMES, not API calls: the CLI emits one `assistant` event per content block, all sharing one usage object. Measured 308 frames / 200 distinct `message.id` and 86 / 54, so a 1.54x-1.59x over-count. (2) `output_tokens` in the stream is a `message_start` PLACEHOLDER: 200 real API messages reported 1,464 output tokens total; the true value exists only in the CLI's own session transcript. (3) `:2607` lets a second `result` in one turn overwrite `state["spend_result"]`, dropping the first round. Plus `:2788` bills `spend_result or spend_sum`, so a small nonzero result SUPPRESSES the sum while a zero result falls through to it.

**The unit is undefined and that is the load-bearing problem.** `_spend_tokens_from_usage:1301` counts cache reads at full weight though they price at ~0.1x and are re-read on every call in a turn. Measured on two real turns: today's raw number is 11.8x-13.6x the effective number (`input + cache_creation + output + 0.1*cache_read` over distinct calls) and 42.7x-42.9x the fresh-only number. So the SAME ledger figure means ~100x different things depending on an unstated choice. `ralph.sh:905-911` already weights cache_read at 0.1, so worker rows and chat rows are in DIFFERENT units in one file.

**Consequence:** no usage cap or monthly limit can be trusted until this lands, because the quantity a cap compares against is not consistent. Sequence the counting work before the limits work.

Four distinct questions share one number today: window occupancy, per-turn spend, period consumption for admission, and money. `_ctx_tokens_from_usage`'s docstring already says spend and occupancy "are different questions and must not share a helper" - the instinct was right and was applied to two of four.
