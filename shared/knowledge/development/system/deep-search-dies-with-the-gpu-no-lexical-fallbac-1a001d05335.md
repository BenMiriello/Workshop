CORRECTED 2026-08-16. This note used to assert that `search()` has no non-vector path and that the plaintext search was not wired in as a fallback. Both were true when it was written and neither is true now; the fix landed in `aa457c8`. The record is kept rather than deleted because the failure mode it describes is real and recurs.

The failure is real. `semantic_index.embed()` raises on any Ollama error, and the local GPU does run out of memory: measured 2026-08-14, `POST 127.0.0.1:11434/api/embed` returned 500 `CUDA error: out of memory`.

What happens now is a degrade, not a 500. `search()` (`semantic_index.py:938`) is hybrid. It tries the vector path first; when `embed()` raises it catches, logs a warning, and scores with BM25 instead (`_bm25_scores`, `semantic_index.py:799`, reached at `:999`). The returned dict carries a `mode` field so the caller and the model can tell how much to trust the result: `"semantic"`, or `"lexical (embedder unavailable: <reason>)"` carrying the underlying error. Re-verified 2026-08-16 by forcing `embed()` to raise `CUDA error: out of memory` against the live index: ranked hits came back with `mode = "lexical (embedder unavailable: CUDA error: out of memory)"` and nothing raised.

BM25 runs over the SAME chunk corpus the vector index embeds, not a second store. `index.meta.jsonl` already holds every chunk's `text`, so the lexical path needs no embedder at all and even a stale index still answers.

`knowledge._plaintext_search` (`knowledge.py:1113`) was NOT the thing wired in, deliberately. It scores `sum(hay.count(t))`: no stopwords, no IDF, no length normalisation, so it ranks by length. Probed against a live scope, a query of pure stopwords returned the same three notes as a real question, and those three were the three largest files. It remains the per-scope note search behind `knowledge.search`, which is a different job from deep search across notes, docs and chats.

Still true, and the real remaining limit: no index, no answer. BM25 reads the built corpus, so a chunk that was never indexed is invisible to both paths. A rebuild is still kicked by a search (`_background_rebuild_if_stale`, `semantic_index.py:633`, called from `search` at `:976`), so a corpus nobody searches is a corpus nobody rebuilds. What changed is that the rebuild no longer blocks: it runs on a background thread, the search answers from whatever is on disk, and the result reports `rebuilding: true` while it catches up.
