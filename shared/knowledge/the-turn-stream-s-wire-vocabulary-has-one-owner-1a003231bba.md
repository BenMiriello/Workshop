The server names an SSE frame with the kind it pushed (`event: <kind>`, routes/chat.py) and the client subscribes by that same string. Nothing enforced the pairing, so `cut` -- the frame carrying WHERE a mid-turn message landed, the whole of decision 0018 -- was pushed by the server and handled by the store's reducer from 2026-08-13 with no listener between them. Effect: the committed transcript placed mid-turn messages correctly while the LIVE view (the streaming tab, the one the operator watches) had no recorded position at all and fell back to the unit index 0018 replaced, resolved against a segment list still growing under it. The message drifted upward through work that preceded it. Reported repeatedly as 'my message shows ABOVE system messages that preceded it' and read each time as a fix that would not hold, because only the committed half was ever fixed.

Now: `frontend/src/components/chat/streamWire.ts` declares every kind the server can send plus its disposition. `useTurnStream`'s handler table is `Record<ConsumedWireKind, ...>` (a consumed kind with no handler does not compile) and listeners are registered by iterating that table (a handler cannot be left unsubscribed). `streamWire.test.ts` scans build_streaming.py and routes/chat.py for emitted kinds and fails naming any the client has never declared. Adding a server stream event means declaring it there first.
