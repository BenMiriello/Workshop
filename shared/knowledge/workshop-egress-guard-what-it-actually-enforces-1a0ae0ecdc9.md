Measured 2026-09-16 in the new-project-5ee20d build sandbox, by loading `~/.claude/hooks/egress-guard.py` read-only and calling its own functions.

**It branches on cwd, and the sandbox defeats that.** `build_project('/workspace')` returns `is_build=False`, so the call falls through to the general anti-exfiltration rule and denies. `build_project('<the real host path of that project tree>')` returns `is_build=True`, slug `new-project-5ee20d`, sensitivity `private`, which the guard ALLOWS. Recognised build roots are `~/workshop/{projects,branches,build-agents}`. The guard is written to let build agents clone and install; the sandbox presenting cwd as `/workspace` is what breaks it. One-line fix: present the real project path, or add the sandbox project root to `_BUILD_ROOTS`.

**It is a command-string filter, not a network control.** The `EGRESS` regex matches tool names: `curl|wget|nc|ncat|netcat|telnet|scp|sftp|rsync|ftp|socat|http|https|xh`. `git` is not among them; `git clone` trips it only because the literal text `https` appears in the command. Consequently it also blocks writing a file whose contents contain a URL, and blocked a read-only diagnostic of its own logic.

Package managers are unmatched and have unrestricted outbound access. Verified: `npm view left-pad version` reaches the registry, `npm install puppeteer` pulled ~650MB of Chromium from Google's servers, `pip install ecmwflibs eccodes` pulled binary wheels from PyPI. So the 'external communication' leg the guard documents itself as closing is not closed. Anything that can run npm, pip or node has full egress. Real enforcement has to happen at the network layer, which is also where the shared-host-network-namespace finding points.
